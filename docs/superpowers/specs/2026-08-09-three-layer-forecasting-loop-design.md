# 销量、库存与补货三层闭环设计

## 目标

在现有订单、库存和预测能力上形成一个可追溯的决策闭环：

```text
已支付订单的日销量事实
    -> 销量需求预测
    -> 按日库存投影
    -> 待确认补货订单草稿
```

该闭环帮助运营人员理解未来可能卖出多少、库存何时不足，以及应准备多少货。它不创建真实采购单、不调用供应商接口、不修改库存，也不把销量预测误称为库存预测。

## 已冻结的业务口径

### 日销量事实

- V1 纳入支付状态为 `paid` 或 `partially_refunded`，且订单状态不是 `canceled` 的订单行数量。
- 当前订单模型尚未保存实际支付成功时间，因此 V1 按已支付订单的**下单创建时间** `placed_at` 归入需求日；页面与 API 必须使用这个准确名称，不能称为“支付成功日销量”。
- 业务时区固定为 `Asia/Shanghai`。一天是当地时间 `[00:00, 次日 00:00)`。
- 已结束的完整自然日才可进入模型训练。当天已支付订单只作为“今日截至当前销量”展示，不被当作完整日训练样本。
- 取消订单直接排除。退款金额不推导 SKU 退货件数；退货率以店铺/SKU 可配置调整项表达，初始默认 `0%`，并在结果中单独披露。

### 库存与供给事实

- 库存预测从某一仓库的当前 `on_hand - reserved` 可用量开始。
- 在途供给必须同时有数量和预计到货日；只在到货日及之后进入库存可用量。
- 缺少预计到货日的在途量不得提前当作可用库存，结果需要标示“到货时间未知”。
- 销量需求的粒度保持 `tenant_id + store_id + sku_id + business_date`；仓库是供给位置，不能将同一店铺 SKU 的需求复制给每个仓库。

### 补货边界

- 补货建议基于提前期、复核周期、安全库存、最低起订量和包装倍数计算。
- 产物始终是 `draft` 待确认补货订单草稿，必须包含计算依据、预计到货日和建议数量。
- 草稿不可自动下单、付款、扣减库存或调用外部采购/物流连接器。

## 推荐架构

### 1. 销量需求预测层

`DemandFactBuilder` 负责从订单行生成日事实，保留来源水位、口径版本、完整日边界和质量标记。`ForecastingService` 仅消费已关闭自然日的事实，以模型注册表选择可复现的销量预测模型，并输出未来每日销售需求与回测指标。

该层输出的是“未来可能卖出多少”，不是库存结论。没有足够完整历史、历史存在缺口或当前日未结束时，必须返回明确质量状态，而不能把未知数据补成真实零销量。

### 2. 库存预测层

`InventoryProjectionService` 对每个未来业务日执行确定性投影：

```text
opening_available = max(0, on_hand - reserved)
daily_available[t] = daily_available[t-1]
                   + scheduled_inbound[t]
                   + return_adjustment[t]
                   - forecast_sales[t]
```

其中 `return_adjustment` 仅来自明确配置的退货率；默认值为零，不能从退款金额猜测。输出包括每日预计可用库存、首次缺货日、未知到货提示和所用输入快照。销量预测改动或库存/在途快照变化时，新的库存投影必须可与旧运行记录区分。

### 3. 补货建议层

`ReplenishmentPlanner` 使用库存投影和补货策略生成草稿：

```text
lead_demand = selected_forecast_sum(lead_time_days)
target_demand = selected_forecast_sum(lead_time_days + review_period_days)
safety_stock = forecast_daily_demand * safety_stock_days
raw_qty = max(0, target_demand + safety_stock - available - dated_inbound)
recommended_qty = apply_moq_then_order_multiple(raw_qty)
```

计算必须固定先后顺序：先得到缺口，再应用最低起订量，最后向上取整到包装倍数。无有效库存快照、无策略或无足够销量历史时不生成误导性数量，只返回可行动的缺失输入说明。

## 界面与接口

库存工作流中的一个 SKU 页面按以下顺序展示：

1. **销量需求预测**：历史实际销量、历史预测对比、未来销售需求；明确需求口径与训练截止日。
2. **库存预测**：当前可用量、锁定量、逐日预计库存、按到货日显示的在途供给、缺货风险及数据缺口。
3. **补货建议**：提前期、复核周期、安全库存、MOQ、包装倍数、建议数量和待确认草稿。

接口返回须把这三层拆开命名，避免客户端将需求量直接展示成库存量。每层返回自身的数据水位、口径/策略版本和质量状态。历史运行及草稿只有在持久化工作包完成后保存；预览调用仍保持无业务副作用。

## 分阶段交付

本设计拆成三项可独立验收的交付，按顺序实施：

1. **需求口径校正**：完整日筛选、已支付订单下单日标签、退货率配置和相关测试。
2. **逐日库存投影**：带预计到货日的在途输入、每日库存路径、缺货日和质量提示。
3. **补货草稿闭环**：策略计算、待确认草稿、三层界面和端到端验证。

不会在本轮加入真实支付成功时间、SKU 级退货明细、采购单执行、供应商接口、自动下单、深度学习模型或新的第三方依赖。这些能力需要独立的数据接入和审批。

## 错误与安全契约

- 所有读取和计划计算必须以租户、店铺、SKU 和仓库边界隔离。
- 历史不足、当天未关闭、库存快照缺失、在途到货日缺失、策略缺失均返回明确的机器可读原因。
- 订单、库存、在途和策略数据的版本/水位必须出现在结果中，便于重新计算和审计。
- 预测结果不保证实际销量或库存；结果必须保留模型、历史窗口和质量说明。
- 任何外部采购动作都必须在独立的人工审批工作流中实现，不能由本闭环触发。

## 验收与反证

- 23:50 下单、次日支付的订单在 V1 按下单日归集，并明确页面标签；取消和未支付订单不计入。
- 当天已支付销量不进入训练历史；跨北京时间午夜的归日结果可复现。
- 到货日在未来第三天的在途量只从第三天开始增加预计库存；未知到货日在途量不能消除缺货风险。
- 退货率默认零，配置后仅以显式调整影响库存投影，不从退款金额反推数量。
- 预测销量、预计库存和建议补货数量三者可分别查看；SKU/店铺/仓库越界读取被拒绝。
- MOQ 与包装倍数的顺序有数值断言，输出为待确认草稿且无采购、库存或连接器副作用。
- 反证至少覆盖：移除取消过滤、允许当天未关闭数据训练、提前计入未知到货在途量时，对应断言必须失败；恢复后复验。
