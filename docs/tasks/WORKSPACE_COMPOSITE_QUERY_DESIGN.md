# 统筹 Agent 复合只读查询设计

## 背景

统筹 Agent 已能逐轮选择并执行多个工具，但当前循环只保存“下一步计划”，没有保存
当前问题中尚未完成的业务子目标。真实模型可能在查完第一项后提前作答；当后续规划或
整理失败时，降级摘要又会全局截断前三条事实，导致后查询的收入等结果丢失。现有多工具
测试通过预设模型决策，无法证明真实模型能完整拆解和收口“库存风险 + 最近收入”一类
复合问题。

闫睿涵 2026-08-12 的人工测试进一步确认：单独库存查询能取得 10 条记录和 4 条优先
关注项，但库存与收入组合查询可能失败或错误回答库存、收入均为 0。这个现象不应通过
添加业务关键词硬路由解决。

## 目标

- 一次识别用户问题中的多个只读业务子目标，并保持到本轮结束。
- 无依赖的只读查询最多三个并发执行；有数据依赖的查询分批串行。
- 每个子目标独立记录成功、无数据、失败或跳过，不让一个失败覆盖其他结果。
- 最终回答覆盖每个子目标，并保持工具返回的核实数字不变。
- 明确区分“没有数据”和“有数据且数值为 0”。
- 降低当前每执行一次工具就重新调用一次规划模型带来的延迟。

## 非目标

- 不执行改价、采购、退款、付款、发布、审批或其他业务写操作。
- 不在本轮实现“查询后生成动作草案、确认、执行、读回、补偿”闭环。
- 不以关键词、正则或模块名称建立确定性语义路由。
- 不新增数据库表、Schema 版本或第三方依赖。
- 不改变各业务模块自身的数据口径和租户隔离规则。

## 方案选择

### 方案 A：只强化现有逐轮 Prompt

要求模型查完全部问题后再作答。改动小，但任务完成状态仍只存在于模型上下文，无法可靠
检测漏查、提前结束或子目标覆盖，不采用。

### 方案 B：一次任务拆解，代码持有只读执行计划（采用）

模型一次输出结构化子目标及依赖；代码校验工具、参数、读权限和依赖图，按批执行并跟踪
完成状态，最后只调用一次整理模型。它不把语义映射硬编码进代码，同时给代码提供可验证的
执行状态和失败边界。

### 方案 C：建立固定业务工作流模板

为“库存+收入”等组合定义固定流程。确定性高，但会持续扩张模板数量并违反 D-034
“确定性代码不做语义路由”，不采用。

## 结构化计划

新增一次性只读计划契约：

```text
WorkspaceReadPlan
  response                         可直接回答时使用
  tasks[]                          1 到 4 个只读子目标

WorkspaceReadTask
  task_id                          本轮唯一、稳定、无业务语义的标识
  objective                        面向店主的简短核对目标
  tool_name                        当前动态目录中的只读工具
  arguments                        工具参数
  depends_on[]                     前置 task_id；默认空
```

计划校验规则：

1. 只允许动态工具目录中 `kind=read` 的工具。
2. 最多四个子目标，同一 `task_id` 不得重复。
3. `depends_on` 只能引用本计划中的任务，必须构成无环图。
4. 完全相同的工具与参数只执行一次；重复目标共享同一核实结果。
5. 店铺、SKU 等范围仍由现有 Pydantic、可信上下文和工具策略校验，规划模型不能扩大权限。
6. 计划里出现写能力、未知工具、循环依赖或无效结构时整份计划拒绝，不执行任何工具。

## 执行模型

执行器按依赖图分批运行：

1. 找出所有前置任务已完成且尚未运行的子目标。
2. 同一批最多三个任务并发；第四个任务等待下一批。
3. 每个任务使用独立参数对象、独立异常边界和同一只读租户上下文。
4. 当前批全部结束后再释放依赖任务，不能因为某一项先返回就提前生成回答。
5. 依赖任务只在前置任务成功时运行；前置失败或无可用结果时标记为跳过，并说明原因。
6. 并发只用于读工具。任何 `kind=generate` 或写动作均不进入本执行器。

第一版采用线程池并发上限 3。SQLite 读连接由各领域服务自行创建；不共享连接、不并发写入。
审计仍按每个工具实际执行记录，汇总响应另保留完整 `tools_used` 和子目标状态。

## 结果契约

每个子目标形成：

```text
task_id
objective
tool_name / tool_label
status = success | no_data | failed | skipped
verified_facts[]
error_summary
data_as_of
```

- `success`：取得可核实记录，允许数值本身为 0。
- `no_data`：证据数为 0、来源明确标记暂无数据，回答为“暂无数据，无法判断”，不能写成 0。
- `failed`：参数拒绝、超时或工具错误；保留其他成功子目标。
- `skipped`：依赖未满足。

最终状态：

- 全部成功：正常完成。
- 至少一项成功、其余失败或无数据：`partial`，回答先给成功事实，再逐项说明未完成边界。
- 全部失败：返回类型化错误，不生成经营结论。
- 全部无数据：明确暂无对应数据，不构造零值结论。

## 回答生成

回答模型接收按用户任务顺序排列的子目标结果，而不是无边界的原始工具 JSON：

- 每个子目标至少保留一条核实事实，不再全局截断前三条。
- 数字、金额、比例和标识符作为不可改写事实传入；最终响应完成后校验关键数字仍可追溯到
  对应子目标。校验失败时使用确定性摘要，不输出模型改写后的数字。
- 最多三项的限制应用于“管理重点”，不用于删除用户明确询问的子目标。
- 模型整理不可用时，按子目标顺序生成确定性中文摘要。

## 范围继承

- 用户明确给出的店铺或 SKU 应进入每个相关子目标。
- 可信 `operator_context` 中的店铺范围继续由现有工具策略注入和验证。
- 一个工具返回的标识符只有在计划声明依赖时，才可作为后续任务输入；禁止从自然语言结果
  猜测标识符。
- 本设计不改变订单工具要求可信 `order_id + shop_id` 的 D-015 门禁。

## 错误与超时

- 每个只读任务拥有独立超时；单项超时不会取消已完成结果。
- 整体请求保持总时限；剩余任务超时时标记失败并返回部分结果。
- 错误信息使用现有产品化映射，不暴露内部工具名、堆栈或数据库字段。
- 规划模型不可用时保持现有安全错误；计划已经生成后，回答模型不可用不影响核实事实返回。

## 验收场景

1. `查看 qingchuan-flagship-001 的库存风险和收入情况`：同时调用库存和
   `gross_revenue`，返回 10 条库存、4 条优先关注、收入 4181.00；任一项失败不得把它写成 0。
2. 三项独立只读查询在同一批最多三个并发执行，回答覆盖三项。
3. 四项独立查询分两批执行，并发峰值不超过 3。
4. 先搜索商品再查竞品的依赖链严格串行；前置无唯一结果时后置任务跳过。
5. 一个任务失败，其他成功时返回 `partial`，成功数字保持原样。
6. 无数据与真实零值分别输出“暂无数据”和“0”。
7. 回答模型故意篡改 4181.00 时触发确定性摘要。
8. 重复工具与参数只执行一次，不重复消耗查询预算。
9. 跨租户、跨店铺参数仍由现有策略拒绝。
10. 改价、采购等请求不进入并行只读执行器，继续走现有确认门禁。
