### 背景和模块说明

落实刘经理对 M6-R 和经营根问题的要求：先搞清销售预测的数据支撑，再结合库存和外部
供货周期形成补货建议；根据产品料号生成**订购单草稿**，由人工确认；同时建立按财务
最终口径扩展的费用底账，只有数据完整时才展示正式净利润。

对应功能：F-326（预测补货与订购单）和 F-327（利润准备度与经营决策台）。

### 模块具体需求

#### 具体需求一：预测输入的正确分层

刘经理列出的数据不是同一类输入，产品必须分层处理：

| 层 | 数据 | 是否阻断基础预测 |
|---|---|---|
| 预测目标 | 历史与当前每日可履约需求/销量事实 | 是；没有可靠目标不运行正式预测 |
| 需求信号 | 曝光、点击、转化、广告趋势、活动、已批准竞品销售区间 | 否；有证据且回测改善后才进入正式模型 |
| 供给约束 | 当前可售库存、在途、MOQ、服务水平、复核周期 | 不阻断销量预测；缺失会阻断或降级补货建议 |
| 交付约束 | 供应商提供的生产/备货周期、运输周期、承诺交期 | 不阻断销量预测；缺失时不得形成正式订购建议 |
| 执行主数据 | 商品、SKU、商家编码、内部料号、供应商 | 料号缺失时不得生成正式订购单草稿 |
| 利润输入 | 收入、采购成本、平台/广告/物流/退货/入库/整备等费用 | 不阻断预测；缺任何必需费用就阻断正式净利润 |

竞品、广告、曝光、点击和转化是候选外生信号。只有 rolling backtest 在相同窗口稳定优于
现有 baseline 且无未来泄漏，才能进入正式 champion；“刘经理列过”不等于模型必须使用。

#### 具体需求二：当前缺口的产品处理

当前没有采购成本、真实订购单、运输周期和二次销售整备成本：

- 正式模式保持 `missing`，页面展示缺什么以及会影响哪个结论。
- Demo 可录入版本化“演示参数”，所有预测后补货、订购单和利润试算必须显式显示该标签。
- 缺失成本不得按 0；缺运输周期不得偷偷用系统默认值生成正式建议。
- 以后由供应商或有权限人员提供交期，系统只收集、展示、跟踪，不核定供应商交期。
- 杨总给出的首单、返单等生产周期只能作为特定商品/供应商场景的人工示例；如以后采用，
  必须由有权限人员按适用料号、供应商和生效期版本化确认，不能写成系统默认值，也不能
  替代当前缺失的运输周期。

#### 具体需求三：订购单边界

产品内统一使用“订购单”，不建设生产工单。V1 单据至少包含：

```text
order_draft_id
tenant_id / store_id
supplier_ref
item_id / sku_id / material_no
recommended_qty / confirmed_qty
unit_cost optional
currency
promised_delivery_at optional
forecast_run_ref / inventory_snapshot_ref / policy_ref
source_summary / assumptions / missing_fields
status / version / created_by / confirmed_by
```

状态机：

```text
draft -> awaiting_confirmation -> confirmed -> in_transit -> received
   └-----------------------> cancelled
confirmed / in_transit ----> overdue
```

- 系统可按料号和已固化补货建议生成 draft，但不得自动进入 confirmed。
- 人工可修改确认数量、供应商和承诺交期，变更形成新版本并保留原建议。
- `confirmed` 只表示内部人工确认，不表示已向供应商成功下单；未来接口必须另有回执。
- V1 的 `in_transit / received / overdue` 只能由有权限人员依据供应商信息或物流凭据手工更新，
  每次更新保存操作者、时间和来源引用；在取得正式接口前不得自动推断状态。
- 不自动采购、付款、修改库存或写入第三方 ERP；只保留以后适配接口。

#### 具体需求四：利润口径与完成门

M10-R 不自行发明财务最终口径。当前产品口径按**签收确认收入**：只有具备可信签收事实的
订单收入才能进入正式利润期间；退款、拒收或签收后退货按版本化政策冲减。以后如财务调整
确认时点，必须发布新的 `revenue_recognition_basis`，不得原地改写历史。

实现采用版本化利润政策，把每笔收入/费用映射为只入账一次的 canonical ledger entry，
并形成三层利润：

| 层级 | 当前含义 | 展示边界 |
|---|---|---|
| 销售利润 | 签收确认收入，扣除退款冲减、采购/销售成本及直接商品成本 | 对应成本齐备才出正式值 |
| 经营利润 | 销售利润继续扣除平台、广告推广、仓储分拣、物流、保险、佣金及退货整备等经营费用 | 费用域不全时显示准备度，不把缺失当 0 |
| 财务最终净利润 | 经营利润继续按批准财务政策计入税费、期间分摊和其他调整 | 仅授权视图展示；政策和必需字段完整才可用 |

三层结果均来自同一 ledger 和利润政策，不为每一层另建一套费用真相。财务最终净利润公式为：

```text
net_profit = sum(included_signed_ledger_entries)
```

政策至少能登记以下收入与费用域及其必需性：

- 签收确认收入、退款/拒收/退货冲减。
- 采购成本/销售成本。
- 包装成本、云仓分拣成本及其他仓储附加费。
- 正向物流、逆向物流、退货入库费用。
- 平台扣点、平台佣金、技术服务费和其他平台费用。
- 运费险。
- 坑位费、服务费、达人/渠道佣金。
- 赠品成本和公益宝贝等订单附加成本。
- 广告与推广费用。
- 退货后二次销售的包装、清洗、熨烫等整备费用。
- 财务最终要求的其他费用、税费或调整项。

##### 当前样本的费用来源与粒度

2026-08-17 的只读表头/粒度审查只作为规划证据，最终以 M7-R WP1/WP2 对受控原文件的
重新校验为准：

| 费用或事实 | 当前可见来源线索 | 当前粒度/限制 | M10-R 处理 |
|---|---|---|---|
| 签收、商家编码、卖家服务费类字段 | 订单导出 | 预计订单级；字段含义、金额方向和单位待复核 | 复核通过后进入订单收入/费用映射，否则缺失 |
| 广告推广花费、淘宝客佣金 | 生意参谋/推广报表 | 以店铺日或报表聚合为主，不能静默摊到订单/SKU | 先保留原始粒度；只有批准的版本化分摊政策才能下钻 |
| 退款金额 | 订单/退款导出 | 不等于退回件数、入库件数或可二次销售数量 | 可作退款冲减候选；件数与整备仍分别保持缺失 |
| 收入账单 | 收入样本 | 月度聚合，不能证明已有完整平台费用明细 | 仅作月度对账输入，不冒充订单级 ledger |
| 其他平台、物流、采购、整备及财务调整 | 当前无可靠明细或未确认 | 来源/粒度/政策缺失 | 人工配置、演示参数或 `missing`，不补零 |

不同粒度的费用不得为了得到单品利润而静默均摊。若财务以后批准订单/SKU 分摊政策，必须
记录 policy version、分摊基数、舍入与余额处理，并保留原始聚合事实和可逆对账关系。

每个域必须记录来源、期间、粒度、币种、金额、版本、对账状态和是否估算。财务政策未确认
或必需域缺失时：

- 对应层级正式字段返回“暂不可核算”及缺失清单；较低层级已完整时可单独展示，不因更高
  层级缺失而一并隐藏。
- 可以展示签收确认收入、已有费用和各层利润准备度。
- 使用演示参数时，销售层和经营层分别显示“销售利润试算（演示参数）”“经营利润试算
  （演示参数）”；最终层只能显示“净利润试算（演示参数）”，不得显示“财务最终净利润”。
- 退款、退货入库和二次销售整备不能重复入账；映射策略和对账反例必须覆盖双算风险。

### 模块验收标准

- 刘经理要求的预测数据支撑点在准备度中逐项可见，缺失项不被伪造。
- M6-R 预测与补货能力被产品化复用，baseline、质量、新鲜度和只读边界无回归。
- 系统能按料号生成订购单草稿，人工确认与供应商交期收集/跟踪跑通，零真实下单/付款。
- 利润底账按签收确认收入并分销售利润、经营利润和财务最终净利润；缺成本时只显示对应
  层级准备度或演示试算，不冒充财务净利润。
- 经营决策台能给出带依据、反证、缺口和确认人的建议，而不是只展示 GMV。
- WP1～WP4 由缪海南完整交付并自测，WP5 由胡磊独立复验签署；
  数值、状态机、隐私、写屏障、浏览器和完整回归门禁通过。

### WP2 M6-R 预测与补货产品化

**任务名称**

M6-R 预测与补货产品化

**任务内容**

复用 M6-R Demand Fact、Forecast Engine 和 Inventory Planning，将其封装为带来源、新鲜度、
风险、缺失条件、批量隔离和只读审核的业务 API，不另建预测算法或模型数值旁路。

**具体需求**

- 建立复用 M6-R Demand Fact、Forecast Engine 和 Inventory Planning 的适配层。
- 提供预测、补货、风险、新鲜度、来源和缺失条件的统一业务 API。
- 支持批量 SKU 运行、单 SKU 失败隔离、显式重跑和只读计划审核。
- 保留 7/14/30 日、P50/P80/P95、backtest、champion reason 和 baseline fallback 语义。

**验收标准**

- 7/14/30 日产品预测、P50/P80/P95、backtest、champion reason 和 baseline fallback 保持。
- 缺日、缺货截断、未知库存、冷启动、旧 forecast/plan 不会冒充高质量 current 结果。
- 同输入、policy、forecast 和库存快照产生相同建议；多仓不复制店铺总需求。
- 缺 lead/transport 等必需约束时仍可返回预测，但正式补货/订购建议被阻断或明确降级。
- 不新建第二套预测算法，不让模型修改预测、champion 或建议量。

### WP3 订购单草稿、人工确认与交付跟踪

**任务名称**

**任务内容**

### WP4 费用底账、利润政策、经营决策台与端到端交付

**任务名称**

费用底账、利润政策、经营决策台与端到端交付

**任务内容**

建立统一 canonical 费用 ledger、签收确认收入政策和三层利润准备度，并把销量、预测、库存、
广告、费用、订购单和模型建议汇总到只读经营决策台，完成真实/人工/演示/缺失全链交付。

**具体需求**

- 定义版本化费用类别、签收确认收入政策、三层利润政策、ledger、来源、期间、粒度、币种和对账状态。
- 提供采购、包装/分拣、平台扣点、运费险、坑位/服务、佣金、赠品/公益、广告、物流、退款、
  退货入库和整备等费用的导入、人工和演示入口。
- 分别计算销售利润、经营利润和财务最终净利润的准备度、缺失项、双算/漏算检查，并隔离正式值与 Demo 试算。
- 展示店铺与单品销量趋势、预测、库存健康、广告 ROI 可用性、三层利润准备度和订购单。
- 提供“建议做什么、依据是什么、还缺什么、需谁确认”的经营建议卡片，模型只解释固化事实。
- 交付真实只读数据、人工配置、演示参数和缺失状态的端到端 Demo 场景与接口/数据模型说明。

**验收标准**

- 单品、订单、日/月和店铺级金额只能按明确分摊政策汇总，不能静默混粒度。
- 任何模型解释都不能修改 ledger、利润金额、完整度或对账状态。
- 点击单品可追到订单/需求、forecast、inventory snapshot、广告/竞品、费用和单据版本。
- 只有数据完整且 Gate 通过时才显示精确补货量或正式净利润；否则显示范围、降级或缺口。
- “提价、备货、清仓”等建议由模型基于固化事实解释，人工确认，页面无自动执行按钮。
- 浏览页面不自动运行预测、生成单据或重算利润；所有运行与创建动作必须显式触发并审计。

## 实现纪律

- Forecast/Plan 的数值、champion、库存公式、利润 ledger 和单据状态由确定性代码控制；
  模型只解释事实、理解用户目标并提出语义建议。
- 不按关键词直接决定提价、补货、清仓或利润结论；关键词和经营标签只可作为 signal。
- 预测目标、候选信号、费用类别、利润政策、单据状态、证据四态和来源类型分别只有一个
  权威定义。
- 本文不预占 schema；实际迁移必须由闫睿涵在 main 刷新 refs 后按权威表登记。
- Eval oracle 与 production input 物理分段，演示参数不得进入 formal Gate 的 ground truth。
